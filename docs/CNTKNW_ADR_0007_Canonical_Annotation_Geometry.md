# ADR-0007 — Canonical Annotation Geometry

**Status:** Accepted
**Date:** 6 August 2026
**Owner:** Lazarus Petrus
**Implements:** AC-003, AC-007, AC-008, AC-009, AC-010, AC-015; NFR-005
**Supersedes:** the opaque `Annotation.geometry` and annotation-level
`textAnchor` fields introduced in Phase 0B

---

## 1. The decision

An annotation is canonical source markup attached to one exact asset and one
1-based PDF page. Its anchor is an explicit discriminated union in normalized,
page-local coordinates. Rendered pixels are a projection of that anchor, never
the stored truth.

The canonical identity is `(sourceId, assetId, page, annotationId)`:

- `sourceId` places the markup in the source workspace;
- `assetId` identifies the actual PDF binary whose page geometry was marked;
- `page` is the PDF's 1-based page number; and
- `annotationId` identifies the independently editable markup entity.

A source may have multiple assets, and its primary asset may be replaced.
Neither a virtualized viewport index, the mounted five-page reader window, a
spacer-derived offset nor a DOM node participates in identity.

## 2. Canonical coordinate space

Canonical coordinates cover the full PDF page box in the page's **unrotated**
frame. The origin is the unrotated top-left. `x` increases left-to-right and
`y` increases top-to-bottom. Points satisfy `0 <= x,y <= 1`. Rectangles use
`x`, `y`, `width`, `height`, all non-negative, and their far edges satisfy
`x + width <= 1` and `y + height <= 1`.

Annotation-local schemas enforce those bounds strictly. The looser shared
`NormalizedPointSchema` and `NormalizedRectSchema` remain unchanged because
they are also used by existing non-annotation source-location contracts. The
trusted geometry boundary clamps only floating-point noise generated by a
valid viewport conversion; arbitrary out-of-range domain input is rejected.

PDF coordinates use a bottom-left origin and may have a non-zero page-box
offset. Conversion therefore has two explicit stages:

1. PDF.js `convertToPdfPoint` or `convertToViewportPoint` /
   `convertToViewportRectangle` handles the current viewport's zoom, offset,
   axis flip and rotation.
2. Pure page-box math converts PDF points to or from normalized unrotated
   coordinates.

The geometry library accepts only a structural viewport and a plain PDF page
box. It imports neither `pdfjs-dist` nor the DOM. Input and output viewport
coordinates are CSS/display pixels local to the page, never canvas backing
pixels. `devicePixelRatio` is consequently absent from the API.

Rotation is a projection concern. A page rotated 90, 180 or 270 degrees keeps
the same canonical anchor. PDF.js applies the current rotation when projecting
that anchor. Axis-aligned viewport rectangles are converted through opposite
corners and normalized by minima/maxima, which is exact for PDF page rotations
in 90-degree increments.

## 3. Anchor types

`Annotation.anchor` is one of four non-interchangeable shapes:

| Anchor | Canonical content | Purpose |
|---|---|---|
| `text` | quote, one or more line rects, their bounding rect, optional offsets/prefix/suffix | selected source text |
| `area` | one rectangle | a page region |
| `point` | one point | a location without an area |
| `ink` | one or more strokes, each containing normalized points | editable freehand/vector paths |

Text selections keep `rects[]`, not one annotation per line. `boundingRect` is
a cached union for hit testing; the per-line rectangles remain authoritative.
`quote` is the selected text. Offsets and prefix/suffix may help exact
reattachment after text extraction changes, but this milestone adds no OCR or
fuzzy matching.

Ink is vector/object data. It is never flattened to canvas pixels, PNG or any
other bitmap. Excalidraw and tldraw are not part of this architecture.

## 4. Annotation kind and anchor mapping

`kind` expresses presentation/interaction intent; `anchor.kind` expresses the
geometry capable of supporting it. The schema enforces this mapping:

| Annotation kinds | Required anchor |
|---|---|
| `highlight`, `underline`, `strike` | `text` |
| `pen`, `arrow` | `ink` |
| `rect`, `ellipse`, `text`, `region` | `area` |
| `bookmark` | `point` |

An arrow is editable path geometry, not a raster or an ambiguous rectangle.
A text annotation is a positioned text box and therefore occupies an area;
its authored content belongs to later annotation UX, not a source-text quote.

The former opaque `geometry` and annotation-level `textAnchor` fields are
removed. Their information is folded into `anchor`. `TextAnchorSchema` in
`shared.ts` remains unchanged because `PdfLocation` and journal
`sourceLocation` still use it for source provenance.

## 5. Annotation and journal truth

Annotations are canonical **source-markup entities**. The continuous journal
remains the canonical knowledge/writing record. `linkedBlockIds` links a
markup entity to existing journal blocks; it does not copy their content or
create an annotation-specific notes store.

A rendered highlight, a journal quote block and a future map projection are
views or linked entities with distinct roles, never three copies of one truth.
Editing a journal block through a projection edits the same block ID. Editing
annotation geometry edits the same annotation ID under the mandatory
optimistic-concurrency guard.

## 6. Asset replacement

Replacing a book's primary PDF creates or selects a different `assetId`.
Existing annotations remain bound to their original asset. Old coordinates
must never silently appear on the replacement binary, even if page counts or
visible text happen to match. A later migration UX may offer explicit,
reviewable reattachment; this milestone provides no automatic migration.

## 7. Schema-v2 migration

Database schema version 2 reuses the existing `annotations` store and indexes.
The Dexie upgrade transaction visits every v1 annotation and replaces
`geometry` plus optional `textAnchor` with `anchor`. No store or second
database is created.

Legacy coordinates are interpreted as follows:

1. Recognized rectangles are read from `rects`, `boundingRect`, `rect`, or
   direct `x/y/width/height` (`w/h` are accepted aliases).
2. Recognized points are read from `point`, direct `x/y`, `points`, or
   `strokes[].points` as appropriate for the mapped kind.
3. If `geometry.normalized` is true, values are already page-normalized. If it
   is false and both positive viewport dimensions exist, x/width are divided
   by viewport width and y/height by viewport height. Values are clamped to
   the page after conversion.
4. Text quote/offset/context values come from the old `textAnchor`; its old
   page is ignored because the annotation's top-level 1-based `page` is
   canonical.
5. Recognized content receives `legacyMigration.geometryStatus = 'converted'`.
   Unmappable content receives a zero-size origin sentinel of the anchor type
   required by `kind` and `geometryStatus = 'fallback'`. The marker makes the
   loss explicit so future UX must not present the sentinel as precise source
   geometry.

The conversion is necessarily lossy for arbitrary opaque v1 `data`, but it is
honest: every record remains present, schema-valid and readable, and fallback
precision is never claimed. The record ID, source, asset, page, kind, style,
links, timestamps and revision are preserved. The upgrade and meta
`schemaVersion = 2` write share Dexie's upgrade transaction; an exception
rolls back the whole version change.

Recovery under NFR-005: close other tabs and reopen to let Dexie retry the
transaction. If the local `cntknw` database cannot be recovered, export or
back up its IndexedDB data before deleting it and reopening. Never delete or
upgrade `philosophy-journal`; it remains a separate read-only legacy source.

## 8. Virtualization, zoom and pixel density

The reader may mount only five pages and replace all others with spacers.
Canonical geometry needs no retained node and no document scroll offset. On a
remount, the current page's PDF page box and viewport are enough to reconstruct
the same projection. Zoom, fit-width, fit-page, resize and
`devicePixelRatio` alter only that projection.

The page number remains 1-based at every domain and geometry-call boundary.
Tests cover first and last pages to prevent a hidden zero-based conversion.

## 9. Accessibility boundary

This milestone intentionally builds no annotation UI. The eventual UI cannot
leave highlights visual-only: annotations need semantic discovery, meaningful
labels and source-linked navigation. Keyboard users must be able to reach an
annotation and move focus between its journal representation and source
region, including after virtualization remounts it. Those interactions belong
to Phase 3B or later and must preserve AC-015.

## 10. Consequences and rejected alternatives

- Geometry survives zoom, resize, reload, view-mode changes, bounded
  virtualization and pixel-density changes because none is stored.
- Asset replacement is safe by identity rather than heuristic similarity.
- Different markup classes cannot smuggle ambiguous shapes through an opaque
  record.
- Freehand edits remain possible because strokes remain vectors.
- The migration has an explicit degraded state instead of deleting records or
  fabricating precision.

Rejected: CSS-pixel persistence, canvas-backing-pixel persistence, viewport
indices, one record per highlight line, page-relative scroll offsets, bitmap
ink, a second annotation database, automatic attachment to replacement
assets, and importing a third-party annotation editor.
